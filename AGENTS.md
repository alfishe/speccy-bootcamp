# AGENTS.md — Technical Article Quality Standards

> **Audience**: AI coding assistants and human contributors.
> Read this before writing or expanding any `.md` file in this repository.

---

## Language & Spelling

- **American English only** — `color`, `behavior`, `initialize`, never `colour`, `behaviour`, `initialise`
- Use clear, direct technical prose — no filler, no hedging, no marketing language
- Prefer active voice: "The ULA generates video" not "Video is generated by the ULA"
- **Hexadecimal**: Use Z80 convention — `#FE`, `#7FFD`, or `$FE`, `$7FFD` for I/O ports and memory addresses. Do NOT use C-style `0xFE` unless explicitly within a C code block.
- **Port addresses**: Always state the port address and its decoding bitmask. The ZX Spectrum uses partial address decoding — many ports are mirrored across address ranges. Document which address lines are actually decoded.

## Three-Track Awareness

This knowledge base covers three parallel hardware streams that share the Z80 CPU and much of the software ecosystem:

| Track | Scope | Primary Models |
|---|---|---|
| **Original** | Sinclair/Amstrad era (1982–1992) | 16K, 48K, 128K, +2, +2A, +3 |
| **Soviet** | Post-Soviet clones (1989–present) | Pentagon, Scorpion, Kay, ATM Turbo, Profi, dozens more |
| **New Gen** | Modern hardware (2010s–present) | ZX Spectrum Next, Sprinter, ZX Evolution (TS-Conf/Baseconf) |

Every article must note which track(s) it applies to. When behavior differs between tracks, document each variant explicitly. Soviet clones are NOT second-class citizens — the ZX Spectrum ecosystem in the post-Soviet space was (and remains) larger than the original Western market.

**Primary research sources by track:**
- **Original**: World of Spectrum (spectrumcomputing.co.uk), Sinclair documentation, Chris Smith's "The ZX Spectrum ULA" book
- **Soviet**: **zx-pk.ru** (the most concentrated knowledge base for Soviet clones — schematics, ROMs, modifications, discussions), nedoPC, TR-DOS documentation
- **New Gen**: ZX Spectrum Next official docs (zxnext.io), TS-Conf documentation, SpeccyWiki

**Track separation rule:** Original-track review articles (e.g., `03_io/peripherals/`, `02_hardware/original/`) must NOT carry full Soviet-clone or New Gen sections. Give them a short **Track Applicability** note (one paragraph with links) and put clone/Next variants in dedicated articles under `02_hardware/clones/` and `02_hardware/newgen/` — e.g., `clone_joysticks.md`, `zx_next_joystick.md`.

## Pre-Flight: Knowledge Base Scan (MANDATORY)

Before writing or expanding any article, you **must**:

1. **Read the root [README.md](README.md)** — it contains the full Documentation Map with every article in the repository. Understand what already exists to avoid duplicating content and to identify cross-linking opportunities.
2. **Scan the section's `README.md`** — know what sibling articles exist in the same folder. Your article should complement, not repeat, adjacent content.
3. **Search for related content** — use grep or file listing to find existing mentions of your topic across the repository. If another article already covers a subtopic in depth, link to it rather than rewriting it.
4. **Check for established patterns** — look at 2–3 exemplary articles in the repository to match style, depth, and structure.
5. **Research the Soviet clone angle** — check zx-pk.ru and related sources for clone-specific behavior, modifications, and extensions. Most Soviet clones have timing differences, extra ports, and expanded memory that the original hardware never had.

> Every article must exist within the knowledge graph. Orphaned articles are unacceptable. Update the root README's Documentation Map when adding new articles.

## Port Decoding & Bitmask Conventions

The ZX Spectrum uses **partial I/O port decoding**. This is critical to document accurately.

### Decoding Rules

- The original 48K ULA decodes only address line **A0** for port `#FE` — any even/odd port pair with A0=0 triggers the ULA. `#FE`, `#01FE`, `#7CFE` all hit the same register.
- The 128K adds decoding for `#7FFD` (bit 15 = 0), `#BFFD` and `#FFFD` for AY-3-8912 access.
- Soviet clones add their own ports with varying decode precision.
- The ZX Spectrum Next has a much more complete port map with specific decode for many functions.

### Bitmask Documentation

When documenting I/O ports, **always** include:

1. **The canonical port address** — the commonly used address
2. **The actual decoding bitmask** — which address lines are checked
3. **Mirroring** — which address ranges alias to the same port
4. **Per-model differences** — if decoding differs between 48K/128K/Pentagon/Next, document each

Format:

```markdown
| Port     | Decoding    | R/W | Description |
|----------|-------------|-----|-------------|
| `#FE`    | A0=0 only   | R/W | ULA: border color (bits 0-2), speaker (bit 4), MIC (bit 3), EAR input (bit 6) |
| `#7FFD`  | A15=0,A1=0  | W   | 128K paging: ROM select, screen select, RAM bank |
```

> [!WARNING]
> Simplified bitmask tables are approximations. **Always verify against hardware schematics and FPGA core implementations.** The Z80 I/O port address space is only 8 bits externally on the ZX Spectrum bus — the ULA and peripherals decode whatever subset of the 16-bit address they choose. Different clones decode differently. Cross-reference with zx-pk.ru discussions and original schematics.

## Article Structure

Every article must follow this skeleton. Omit sections that genuinely don't apply, but the **Overview** and **Navigation** are mandatory.

### 1. Navigation Breadcrumb (line 1)

```markdown
[← Home](../README.md) · [Section Name](README.md)
```

### 2. Title

Use a single `#` heading. Include the subject and a subtitle with key subtopics:

```markdown
# Z80 Interrupts — IM0, IM1, IM2, Vector Tables, Timing
# Beeper Audio — 1-Bit Sound Synthesis, Pulse-Width Modulation, Multi-Channel Engines
# Pentagon 128K — The Most Popular Soviet ZX Spectrum Clone
```

### 3. Overview

The first section after the title. Two distinct styles depending on article type — choose before you write.

---

#### Type A: Concept Articles (history, hardware architecture, subsystem deep-dives)

These articles answer *why* something exists and *what changed because of it*. The overview should be **scannable and alive** — a reader understands scope in under 10 seconds *and wants to keep reading*.

**Planning checklist** (answer these, then write prose that embeds the answers naturally):

| Question | What it means |
|---|---|
| **What is it?** | Define the thing, its scope, and where it lives. |
| **What was the problem?** | Why does this exist? Concrete pain, not abstract need. |
| **How does it work / how did it evolve?** | Core mechanism or historical arc. |
| **Why does it matter?** | What changed? Numbers, not adjectives. |

**Voice:**

- **Open with a hook.** A contradiction, a surprise, a concrete image. "The ZX Spectrum had no sound chip, no sprite engine, no scroll hardware — and its demoscene still produced effects that make people stare in disbelief."
- **Write like you're explaining to a smart colleague at a bar.** Short sentences. Concrete nouns (T-states, scanlines, ports, clock cycles). No filler.
- **Bold vivid details, not section labels.** Bold `**69888 T-states per frame**`, not `**The timing.**`.
- **Paragraphs tell a story.** Hook → problem → solution arc → punchline. 2–5 sentences each.
- **Every paragraph gets a blank line after it.** Never a monolithic block.

---

#### Type B: Reference Articles (register catalogs, port maps, opcode tables, file format specs)

These articles exist to be **looked up**, not read cover-to-cover. The overview must be minimal: state what the thing is, where it lives, and get out of the way.

**Template (one paragraph, 2–4 sentences):**

> [Thing] is [definition — one sentence]. It lives in [hardware / I/O port / file format]. See [cross-link] for the broader context.

**Rules:**
- No hook. No drama. No story arc. The reader came here to look up a port address or an opcode — don't waste their time.
- State the port address, register name, or file signature so the reader knows they're in the right place.
- One paragraph only. No blank-line separation.
- Never stretch to fill space — if 2 sentences cover it, stop.

### 4. Architecture / How It Works

- Use **Mermaid diagrams** for system relationships, data flows, and state machines
- Show where the component sits in the overall system (ULA, CPU bus, expansion port)
- Explain the **hardware backing** — which chips, which I/O ports, which bus interactions
- For Soviet clones: explain what differs from the original hardware and why

### 5. Data Structures & Register Tables

- Show the **actual Z80 I/O port map** or register layout with inline comments
- Follow with a **field description table** for non-obvious fields
- Include the schematic reference: `/* Ferranti ULA 5C/6C — 48K */`
- Annotate critical constraints inline: `/* Contended I/O — add 1 T-state wait! */`
- **I/O Port Tables**: Documentation must use the following table format:
  ```markdown
  | Port     | Decoding    | R/W | Description |
  |----------|-------------|-----|-------------|
  | `#FE`    | A0=0        | R/W | ULA border/beeper/MIC/EAR |
  ```

### 6. API Reference / ROM Routine Reference

- Show ROM routine entry points with addresses: `/* #0D5B — BEEP */
- Include practical Z80 assembly usage snippets immediately after each routine
- Group related functions together
- Document which ROM version (48K, 128K, Russian) provides the routine

### 7. Decision Guides & Comparison Tables

When multiple approaches exist, provide a **decision matrix**:

```markdown
| Criterion | Option A | Option B |
|---|---|---|
| When to use | ... | ... |
| Limitation | ... | ... |
```

### 8. Historical Context & Modern Analogies (MANDATORY for architectural topics)

This is **not optional** for any article covering a fundamental or architectural concept.

**Historical perspective:**
- Include a **competitive landscape** table comparing to contemporary platforms (C64, Amstrad CPC, MSX, Atari 8-bit, NES, BBC Micro)
- Explain what made the ZX Spectrum's approach innovative (or not) relative to its era
- Provide **pros/cons analysis** in the context of 1982–1994 hardware constraints
- For Soviet clones: explain the cultural and economic context — why the Spectrum became the dominant platform in the post-Soviet space

**Modern analogies:**
- Add a **comparison table** mapping ZX Spectrum concepts to modern equivalents
- Help modern developers build intuition by connecting unfamiliar retro concepts to things they already know

### 9. Practical Examples

- Every article must include at least one **complete, working code example**
- Examples must assemble — no pseudocode unless explicitly marked
- Z80 assembly (sjasmplus syntax preferred), C (z88dk/SDCC), or Sinclair BASIC as appropriate
- Show the full lifecycle: init → use → cleanup
- Annotate non-obvious lines with inline comments
- Include T-state counts for timing-critical code

### 10. When to Use / When NOT to Use

Every API or subsystem article must include explicit guidance on:
- **When to use** — the ideal scenarios, applicability ranges, sweet spots
- **When NOT to use** — situations where a different approach is better, with explanation of why
- **Applicability ranges** — quantify limits (e.g., "beeper music can produce 4-6 simultaneous voices at 3.5 MHz with careful cycle counting")

### 11. Best Practices & Antipatterns

- **Best practices**: Numbered list of actionable recommendations. Each item should be one line.
- **Antipatterns**: Common bad habits that assemble but produce subtle bugs, poor performance, or system instability. Show the antipattern and the correct alternative side by side.

### 12. Pitfalls & Common Mistakes

- Use a dedicated **Pitfalls** section near the end
- Each pitfall gets a numbered subsection with:
  - A **bad code example** showing the bug
  - An explanation of **why** it fails
  - The **correct** version

### 13. Use Cases

Provide real-world use cases that demonstrate practical application:
- What kind of software uses this feature?
- Which well-known ZX Spectrum titles or demos relied on it?
- What are the common integration patterns?

### 14. FAQ (when topic resonates)

For topics that commonly generate questions, include a short FAQ section addressing the most frequent developer questions.

### 15. References

- Schematic references and hardware datasheets
- Cross-links to related articles in this repository
- External links where authoritative (zx-pk.ru, World of Spectrum, ZX Spectrum Next docs, Z80 user manual)
- Book references (Chris Smith's ULA book, Rodnay Zaks "Programming the Z80", Complete Spectrum ROM Disassembly)

## Formatting Standards

### Memory Maps

- When illustrating memory layouts, screen layouts, or file format structures, use **monospace ASCII box-drawing** (`┌─┐`) rather than Mermaid flowcharts. Mermaid is for logic/state; ASCII boxes are for byte-precise memory layouts.

### Reverse Engineering & Patching

When documenting reverse engineering efforts:
- **Disassembly**: Use standard Z80 disassembly blocks with file offsets and original hex bytes included.
- **Unified Patch Tables**: Use the exact table structure below:
  ```markdown
  | File Offset | Original  | Patched   | Assembly         | Rationale |
  |-------------|-----------|-----------|------------------|-----------|
  | `#1A4`      | `CA 1E 0D`| `C3 00 00`| `JP #0000`       | Redirect to custom handler |
  ```
- **Call Graphs**: Use Mermaid diagrams for call graphs.

### Tables

- Use tables for structured comparisons, flag lists, port maps, field descriptions
- Always include a header row and separator
- Keep cells concise — one concept per cell

### Code Blocks

- Use fenced code blocks with language tags: ` ```z80 `, ` ```c `, ` ```basic `
- Use `; comment` for Z80 assembly inline annotations
- Use `/* comment */` for C code annotations

### Mermaid Diagrams

- Use for architecture diagrams, data flow, state machines, and system relationships
- Keep diagrams readable — no more than ~15 nodes per diagram

### Alerts

Use GitHub-style alerts sparingly for critical information:

```markdown
> [!NOTE]
> Background context that aids understanding

> [!WARNING]
> Common mistake that causes crashes or data corruption
```

- **The Contention Alert**: Any code or timing reference that involves contended memory or I/O must be highlighted with a `> [!WARNING]` block explicitly stating **Requires contended memory timing** — the Z80 is stalled by the ULA during specific cycles and naive timing calculations will be wrong.

### Horizontal Rules

Use `---` to separate major sections. Don't use between subsections.

## Depth Expectations

### Shallow (unacceptable)

A port address dump with no context, no explanation of decoding, no examples, no pitfalls. This is a datasheet, not documentation.

### Adequate

Overview + port/register descriptions + one example + references. Functional but not a learning resource.

### Deep (target quality)

Everything above, plus:
- Architectural diagrams showing hardware relationships
- Historical context and competitive landscape
- Modern analogies for accessibility
- Decision guides for choosing between approaches
- Multiple examples covering common and edge cases
- Comprehensive pitfalls with bad/good code pairs
- Performance analysis with quantified T-state costs
- Cross-references to related articles
- Soviet clone and New Gen variants documented
- Port decoding bitmask verification

**Every article in this repository should target "Deep" quality.**

## What Makes an Exemplary Article — Key Differentiators

### 1. The "Why It Exists" Opening

Every great article opens by answering *why* someone should care — not just what the thing is.

- ✗ *"Port #FE is used for border color and sound."*
- ✓ *"The ZX Spectrum had no dedicated sound chip and no video border control register. Instead, a single I/O port — `#FE` — handled border color, the 1-bit speaker, the MIC output, and the EAR input, all crammed into 8 bits. Every Spectrum program that makes a beep or changes the border hits this one port."*

### 2. Multi-Phase Architecture Diagrams

Great articles don't just describe a process — they break it into **numbered phases** with Mermaid diagrams at each stage.

### 3. Named Antipatterns with Bad/Good Pairs

The best articles give antipatterns memorable names:
- "The Contention Ignorer" (timing code that doesn't account for ULA wait states)
- "The Port Collision" (using a port without checking decoding conflicts with clone hardware)
- "The Floating Bus Gambler" (reading uncontended port values without understanding what's on the bus)

Each antipattern shows the **broken code**, explains **why it breaks**, and provides the **corrected version**.

### 4. Decision Flowcharts

When multiple approaches exist, include a Mermaid decision flowchart.

### 5. Use-Case Cookbooks

Beyond toy examples, exemplary articles include a **cookbook** of real-world patterns.

### 6. Quantified Performance Tables

Great articles provide concrete numbers:
- "LDIR at 3.5 MHz: 21 T-states per byte — 166 KB/s throughput"
- "Beeper frequency range at 3.5 MHz: 54 Hz to 55,930 Hz"
- "Contention adds 1-6 T-states per contended memory access during screen draw"

### 7. Cross-Platform Comparison Tables

The best articles include a comparison table that maps ZX Spectrum concepts to their equivalents on other platforms.

### 8. Memory Safety Checklists

For any code that involves memory paging, stack manipulation, or interrupt handling, include a **risk/cause/prevention** table.

### 9. The "Impact on FPGA/Emulation" Section

Note implementation concerns for hardware reproduction: timing-sensitive code, floating bus behavior, contention timing, port decode edge cases.
If article is related completely to the software and has no relationship with FPGA/Emulation — just omit it.

## Research Methodology

Before writing or expanding an article:

1. **Web research** — Search for real-world usage, developer forum discussions, and existing technical analyses.
2. **zx-pk.ru research** — For Soviet clone topics, search zx-pk.ru forums. This is the most concentrated knowledge base for Pentagon, Scorpion, Kay, ATM Turbo, Profi, and dozens of other clones. Schematics, ROM listings, modification guides — it's all there.
3. **Cross-reference hardware documentation** — Verify port decoding, timing, and register behavior against schematics and datasheets.
4. **Study real software** — Reference well-known ZX Spectrum titles, demos, and applications that use the feature.
5. **Check modern parallels** — Research whether the concept has modern equivalents.
6. **Verify port decoding bitmasks** — Do NOT trust simplified bitmask tables without verification. Cross-reference with hardware schematics and FPGA core source code.
7. **Scan this repository first** — Follow the Pre-Flight Knowledge Base Scan procedure above.

## Content Principles

1. **Hardware grounding** — Always explain which chip, which port, which bus cycle. The ZX Spectrum is a hardware platform; software docs without hardware context are incomplete.

2. **No placeholders** — Every code example must be complete enough to assemble. Every port must show the real address with decoding. Every register must show the real bit layout.

3. **Per-model accuracy** — Always specify which model behavior applies to (48K, 128K, +2, +2A, +3, Pentagon, Scorpion, etc.). When behavior differs, document each variant.

4. **Little-Endian Warning** — The Z80 is **Little-Endian**. Modern developers coming from x86 will be comfortable, but those coming from the Amiga (68000) or ARM (configurable) must be reminded.

5. **Honest trade-offs** — When a hardware feature is severely limited, say so. The ZX Spectrum has no sprites, no smooth scroll, no dedicated sound chip (original 48K), and color clash is a real constraint. Don't oversell.

6. **Cross-linking** — Every article should link to at least 2–3 related articles. The documentation is a graph, not a list.

7. **Source attribution** — Cite schematics, datasheets, ROM disassembly listings, and book references. This is a technical reference, not folklore.

8. **De-abbreviation** — When introducing abbreviations (ULA, AY, PSG, DMA, TR-DOS, ESXDOS), always provide the full name on first use and include a full-name column in summary tables.

9. **Real-world grounding** — Every feature must be contextualized with real use cases, applicability ranges, and honest guidance on when to use alternatives.

10. **Contention awareness** — Any article involving timing must address memory contention. The ULA steals bus cycles from the CPU during screen draw. This is not optional knowledge — it's fundamental to every performance-critical ZX Spectrum program.
